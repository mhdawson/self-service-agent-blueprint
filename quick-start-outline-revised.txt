# Self-Service Agent Blueprint: Quick Start Guide
## Revised Outline

================================================================================
1. INTRODUCTION
================================================================================

1.1 Who Is This For?
  - IT teams implementing AI-driven self-service solutions
  - DevOps engineers deploying agent-based systems
  - Solution architects evaluating AI automation platforms
  - Organizations looking to streamline IT processes with generative AI

1.2 The Business Case for AI-Driven IT Self-Service

Many organizations are working to support IT processes through generative AI based
self-service implementations. IT teams with Red Hat have already started on this
journey and the team building this quickstart met with those teams to incorporate
the lessons learned so far into the quickstart.

The key value proposition for implementing IT processes with generative AI include:

* Reduced employee time to complete common requests. The system helps employees
  create their requests by helping them understand the options and required
  information for the request and helps employees submit those requests once
  they are ready.
* Higher compliance to process standards. Requests will be more complete and
  aligned with process standards. This will reduce the need to contact the
  requesting employee for additional information and reduce time and effort to
  review and complete requests.
* Fewer rejected requests due missing/incorrect information. Rejected requests
  are frustrating for employees and leads to lower employee satisfaction.
  Avoiding request rejection and reducing back and forth on requests will
  improve employee satisfaction.
* Shorter time to close a ticket. The system helps tickets to close faster,
  improving throughput and reducing ticket idle time.

1.3 Example Use Cases

IT processes that are suitable for automation with generative AI include:

* Laptop refresh requests
* Privacy Impact Assessment (PIA) assessment
* RFP generation
* Access request processing
* Software license requests
* Equipment provisioning

1.4 What This Quickstart Provides

This quickstart provides the framework, components and knowledge to accelerate
your journey to deploying generative AI based self-service implementations. Many
AI based IT process implementations should be able to share common components
within an enterprise. The addition of an Agent configuration file, along with
additional tools, knowledge bases and evaluations complete the implementation
for a specific use case. Often no code changes to the common components will be
required to add additional tools, knowledge bases or agents.

1.5 What You'll Build

The quick start provides implementations of the common components along with the
process specific pieces needed to support the laptop refresh IT process as a
concrete implementation.

Time to complete: 30-60 minutes (depending on deployment mode)

By the end of this quickstart, you will have:
- A fully functional AI agent system deployed
- A working laptop refresh agent with knowledge bases and tools
- Completed evaluation runs demonstrating agent quality
- (Optional) Slack integration for real-world testing
- Understanding of how to customize for your own use cases

* OpenShift cluster with:
  - OpenShift Serverless Operator
  - Streams for Apache Kafka Operator
* Access to LlamaStack/LLM endpoint

* OpenShift cluster access (for Helm deployment)

3. ARCHITECTURE & DEPLOYMENT MODES
================================================================================

3.1 Two Deployment Modes

This blueprint supports two deployment modes to match your development stage
and infrastructure:

MODE 1: TESTING (Mock Eventing)
  When to use: Initial deployment, CI/CD pipelines, integration testing, staging environments
  Communication: Mock eventing service mimics Knative behavior
  Infrastructure: Kubernetes (no special operators)
  Deployment: Kubernetes/OpenShift
  Best for: Getting started, development, testing event-driven flows without Knative infrastructure

MODE 2: PRODUCTION (Knative Eventing)
  When to use: Production deployments, high-scale systems
  Communication: Full Knative eventing with Kafka
  Infrastructure: OpenShift + Serverless + Kafka operators
  Deployment: OpenShift
  Best for: Production workloads, scalability, reliability

DECISION MATRIX:

| Aspect           | Testing     | Production |
|------------------|-------------|------------|
| Infrastructure   | Basic       | Full       |
| Scalability      | Medium      | High       |
| Reliability      | Good        | Enterprise |
| Setup Complexity | Low         | High       |
| Cost             | Low         | Higher     |

3.2 Core Architecture Flow

Both modes use the same core components and logic:

REQUEST FLOW:
1. User initiates request (Slack, API, CLI, Web)
2. Request Manager normalizes and validates request
3. Agent Service processes with LlamaStack and tools
4. Integration Dispatcher delivers response to user

The communication mechanism (Mock Events vs Knative Events) is
abstracted via the Strategy Pattern - same business logic, different transport.

SESSION MANAGEMENT:
* Request Manager: Tracks user interactions across integrations
* Agent Service: Manages LlamaStack agent conversation history
* Database: PostgreSQL stores all session state

INTEGRATION SUPPORT:
* Bidirectional: Slack (receives and sends)
* Request-only: Web, CLI, API (synchronous response)
* Response-only: Email, SMS, Webhook (delivery only)

3.3 Communication Architecture

[Reference to ARCHITECTURE_DIAGRAMS.md for detailed flow diagrams]

KEY PATTERN:
  External System → Request Manager → Agent Service → Integration Dispatcher → User

UNIFIED CODEBASE:
* Same code runs in both modes
* Environment variable controls broker URL for mock vs production eventing
* Strategy pattern abstracts communication mechanism
* No code changes needed to switch modes

4.1 CORE PLATFORM COMPONENTS (Reusable Across Use Cases)

────────────────────────────────────────────────────────────────────────────
4.1.1 Request Manager
────────────────────────────────────────────────────────────────────────────

PURPOSE:
Central request orchestrator that normalizes incoming requests from all
channels (Slack, API, CLI, Web) and routes them to the appropriate agent.

WHY IT MATTERS:
* Single entry point for all requests simplifies architecture
* Normalizes diverse integration formats into standard request structure
* Manages session continuity across multiple user interactions
* Provides consistent API regardless of communication channel

IN THE LAPTOP REFRESH EXAMPLE:
* Receives laptop refresh requests from Slack users or CLI tools
* Maintains conversation context across multiple turns
* Routes requests to the routing agent initially
* Tracks request history and user metadata

REUSABILITY FOR OTHER USE CASES:
No changes needed - Request Manager is fully generic. It works with any
agent configuration and integration type.

────────────────────────────────────────────────────────────────────────────
4.1.2 Agent Service
────────────────────────────────────────────────────────────────────────────

PURPOSE:
AI processing engine that integrates with LlamaStack to execute agent
interactions, call tools, and generate responses.

WHY IT MATTERS:
* Handles all LLM interactions and agent orchestration
* Manages tool calling and integration with MCP servers
* Streams responses for better user experience
* Maintains LlamaStack session state for coherent conversations

IN THE LAPTOP REFRESH EXAMPLE:
* Executes the routing agent to determine user intent
* Runs the laptop refresh specialist agent to handle the request
* Calls ServiceNow MCP to check eligibility and create tickets
* Calls Employee Info MCP to retrieve employee data
* Uses laptop refresh knowledge base for policy questions

REUSABILITY FOR OTHER USE CASES:
No changes needed - Agent Service is generic. Register your agents and
tools via Asset Manager, and Agent Service will orchestrate them.


────────────────────────────────────────────────────────────────────────────
4.1.3 Integration Dispatcher
────────────────────────────────────────────────────────────────────────────

PURPOSE:
Multi-channel delivery hub that sends agent responses to users via their
preferred communication channels (Slack, Email, SMS, Webhooks).

WHY IT MATTERS:
* Decouples agent logic from delivery mechanisms
* Supports multiple communication channels without agent changes
* Manages delivery reliability and retry logic
* Handles integration-specific formatting and protocols

IN THE LAPTOP REFRESH EXAMPLE:
* Delivers laptop options and status updates to Slack
* Sends confirmation emails when tickets are created
* Handles Slack incoming events (button clicks, messages)
* Manages integration defaults and user preferences

REUSABILITY FOR OTHER USE CASES:
No changes needed for standard channels. Add new integration handlers only
if you need custom delivery mechanisms.

────────────────────────────────────────────────────────────────────────────
4.1.4 Asset Manager
────────────────────────────────────────────────────────────────────────────

PURPOSE:
Configuration manager that registers agents, knowledge bases, and tool
groups with LlamaStack.

WHY IT MATTERS:
* Simplifies agent configuration and deployment
* Automates knowledge base creation from text files
* Manages tool group registration for MCP servers
* Provides version control for agent configurations

IN THE LAPTOP REFRESH EXAMPLE:
* Registers routing agent and laptop refresh specialist agent
* Creates laptop refresh knowledge base from policy documents
* Registers ServiceNow and Employee Info tool groups
* Configures agent instructions and system prompts

REUSABILITY FOR OTHER USE CASES:
Highly reusable - add your agent configs, knowledge bases, and tools to
config/ directories. Asset Manager handles registration automatically.

4.1.5 Mock Eventing Service

WHY IT MATTERS:

IN THE LAPTOP REFRESH EXAMPLE:
* Used in testing mode for CI/CD pipelines

REUSABILITY FOR OTHER USE CASES:
Fully reusable - no customization needed. Enable with helm-install-test.

4.2 LAPTOP REFRESH SPECIFIC COMPONENTS

────────────────────────────────────────────────────────────────────────────
4.2.1 MCP Servers (Model Context Protocol)
────────────────────────────────────────────────────────────────────────────

WHAT IS MCP?
Model Context Protocol is a standard for connecting AI agents to external
systems and tools. MCP servers expose tools that agents can call during
conversations.

PURPOSE:
Enable agents to interact with external systems (databases, APIs, services)
by exposing tools through a standardized protocol.

WHY IT MATTERS FOR AI-BASED IT PROCESSES:
* Agents need access to real data (employee info, ticket systems)
* Tool calls enable agents to take actions (create tickets, update records)
* Standardized protocol makes tools reusable across agents
* Separates business logic from agent orchestration

IN THE LAPTOP REFRESH EXAMPLE:

  ServiceNow MCP Server:
  * get_current_laptop - Retrieves employee's current laptop info
  * check_refresh_eligibility - Verifies if employee qualifies for refresh
  * create_laptop_refresh_ticket - Submits refresh request to ServiceNow
  * get_available_laptops - Fetches laptop options by region

  Employee Info MCP Server:
  * get_employee_info - Retrieves employee details (name, location, role)
  * Used for personalizing responses and validating requests

REUSABILITY FOR OTHER USE CASES:
* ServiceNow MCP can be reused for other SNOW-based workflows
* Employee Info MCP is reusable across any employee-facing process
* For new use cases, create new MCP servers for your specific systems
* Framework is fully generic - just implement your tools

────────────────────────────────────────────────────────────────────────────
4.2.2 Knowledge Bases
────────────────────────────────────────────────────────────────────────────

PURPOSE:
Vector databases containing domain-specific knowledge that agents use for
Retrieval-Augmented Generation (RAG) to answer questions accurately.

WHY IT MATTERS FOR AI-BASED IT PROCESSES:
* Provides agents with accurate, up-to-date policy information
* Reduces hallucination by grounding responses in factual documents
* Enables easy updates without retraining models
* Supports complex policies that exceed LLM context windows

IN THE LAPTOP REFRESH EXAMPLE:
* laptop-refresh knowledge base contains:
  - refresh_policy.txt: Eligibility rules, warranty requirements
  - laptop_offerings.txt: Available models by region, specifications
* Agent retrieves relevant policy sections to answer user questions
* Ensures compliance with organizational policies

REUSABILITY FOR OTHER USE CASES:
Highly reusable pattern:
1. Create directory in asset-manager/config/knowledge_bases/
2. Add .txt files with your domain knowledge
3. Asset Manager creates vector database automatically
4. Configure your agent to use the knowledge base

Examples for other use cases:
* PIA Assessment: privacy_laws.txt, assessment_templates.txt
* RFP Generation: rfp_guidelines.txt, vendor_requirements.txt

────────────────────────────────────────────────────────────────────────────
4.2.3 Agents
────────────────────────────────────────────────────────────────────────────

PURPOSE:
AI agent configurations that define agent behavior, instructions, tools,
and knowledge bases.

WHY IT MATTERS FOR AI-BASED IT PROCESSES:
* Defines agent personality and behavior
* Specifies which tools and knowledge the agent can access
* Enables specialized agents for different processes
* Supports routing patterns for complex workflows

IN THE LAPTOP REFRESH EXAMPLE:

  Routing Agent (routing-agent):
  * Greets users and identifies their intent
  * Routes to appropriate specialist agent
  * Handles general questions
  * No tools or knowledge bases (pure routing)

  Laptop Refresh Specialist Agent (laptop-refresh):
  * Specialized in laptop refresh process
  * Uses laptop-refresh knowledge base
  * Calls ServiceNow and Employee Info tools
  * Guides users through request creation
  * System prompt includes process steps and compliance rules

REUSABILITY FOR OTHER USE CASES:
Agent configuration pattern is highly reusable:
1. Create YAML file in asset-manager/config/agents/
2. Define agent name, instructions, tools, knowledge bases
3. Asset Manager registers with LlamaStack
4. Update routing agent to route to new specialist

Example for PIA Assessment:
* Create pia-specialist agent
* Use privacy knowledge base
* Call compliance checking tools
* Add routing rule for PIA requests

────────────────────────────────────────────────────────────────────────────
4.2.4 Evaluation Framework
────────────────────────────────────────────────────────────────────────────

PURPOSE:
DeepEval-based testing system that validates agent behavior against
business requirements and quality metrics.

WHY IT MATTERS FOR AI-BASED IT PROCESSES:
* Ensures agents meet business requirements before deployment
* Catches regressions when updating prompts or models
* Provides metrics for continuous improvement
* Validates compliance with policies and procedures
* Builds confidence in AI system reliability

IN THE LAPTOP REFRESH EXAMPLE:

  Predefined Conversation Flows:
  * Success flow: Complete laptop refresh request
  * Edge cases: Ineligible employee, missing information
  * Saved in evaluations/conversations_config/conversations/

  Generated Conversations:
  * Synthetic conversations with varied scenarios
  * Tests agent handling of diverse user inputs

  Evaluation Metrics:
  * Information Gathering: Did agent collect employee ID?
  * Policy Compliance: Did agent check eligibility correctly?
  * Option Presentation: Were laptop options shown accurately?
  * Process Completion: Was ticket created successfully?
  * Flow Termination: Proper ending with ticket number
  * User Experience: Helpfulness, clarity, professionalism

  Pipeline:
  1. Run conversations against deployed agent
  2. Generate additional test scenarios
  3. Evaluate with business metrics
  4. Report results and identify issues

REUSABILITY FOR OTHER USE CASES:
Evaluation framework is reusable with customization:

1. Define conversation templates for your use case
2. Create custom metrics in get_deepeval_metrics.py:
   * For PIA: Check if all privacy questions were asked
   * For RFP: Validate RFP structure and completeness
3. Run evaluation pipeline: python evaluate.py
4. Review results and iterate

The framework structure (conversation execution, generation, evaluation)
remains the same - only metrics and templates change.

5.5 Common Issues and Troubleshooting

Issue: Pods stuck in Pending state
Solution: Check resource quotas and limits in namespace

Issue: Agent returns errors about missing tools
Solution: Verify asset manager job completed successfully

Issue: LlamaStack connection errors
Solution: Check LLAMA_STACK_URL environment variable

Issue: Evaluation fails with authentication errors
Solution: Verify LLM_API_TOKEN is set correctly

Issue: Slack events not received
Solution: Check Integration Dispatcher route is accessible externally

See TROUBLESHOOTING.md for more details.

7. CUSTOMIZING FOR YOUR USE CASE
================================================================================

The laptop refresh example demonstrates all components. This section guides
you in adapting the blueprint for your own IT process.

7.1 Planning Your Use Case

────────────────────────────────────────────────────────────────────────────
STEP 1: Define Your IT Process
────────────────────────────────────────────────────────────────────────────

Questions to answer:
* What IT process are you automating? (PIA, RFP, access requests, etc.)
* What are the steps a user goes through?
* What information does the agent need to collect?
* What systems does the agent need to interact with?
* What policies or rules govern the process?
* How do you measure success?

Example: Privacy Impact Assessment (PIA)

Process steps:
1. User requests PIA assessment
2. Agent asks about project details (name, scope, data types)
3. Agent asks privacy-specific questions
4. Agent evaluates risk level based on responses
5. Agent generates PIA document
6. Agent submits to compliance team

────────────────────────────────────────────────────────────────────────────
STEP 2: Identify Required Integrations
────────────────────────────────────────────────────────────────────────────

For each external system, determine:
* What data do you need to read?
* What actions do you need to perform?
* Does an API exist?
* What authentication is required?

Example: PIA Assessment
* Compliance system API: Submit PIA documents
* HR system: Get employee and project info
* Document storage: Save generated PIAs
* Email: Notify compliance team

────────────────────────────────────────────────────────────────────────────
STEP 3: Map Knowledge Requirements
────────────────────────────────────────────────────────────────────────────

What knowledge does the agent need?
* Policy documents
* Process guidelines
* Templates
* FAQs
* Legal/compliance requirements

Example: PIA Assessment
* Privacy laws and regulations
* PIA question templates
* Risk assessment criteria
* Data classification guidelines
* Example PIAs for reference

────────────────────────────────────────────────────────────────────────────
STEP 4: Define Success Metrics
────────────────────────────────────────────────────────────────────────────

How will you evaluate the agent?
* Process completion rate
* Information accuracy
* Policy compliance
* User satisfaction
* Time to completion

Example: PIA Assessment
* Did agent ask all required privacy questions?
* Was risk level assessed correctly?
* Did generated PIA meet compliance standards?
* Was submission successful?

────────────────────────────────────────────────────────────────────────────

7.2 Implementation Checklist

Use this checklist to implement your use case:

[ ] CREATE MCP SERVERS
    Directory: mcp-servers/your-use-case/

    Steps:
    1. Copy mcp-servers/employee-info/ as template
    2. Define tools for your system APIs
    3. Implement tool functions
    4. Add authentication
    5. Write unit tests
    6. Update Containerfile
    7. Add to Makefile build targets

    Example tools for PIA:
    * get_project_info
    * assess_privacy_risk
    * generate_pia_document
    * submit_to_compliance

[ ] BUILD KNOWLEDGE BASE
    Directory: asset-manager/config/knowledge_bases/your-use-case/

    Steps:
    1. Create directory
    2. Add .txt files with domain knowledge
    3. Organize by topic
    4. Keep documents focused (< 2000 words each)
    5. Update regularly

    Example for PIA:
    * privacy_laws.txt
    * pia_questionnaire.txt
    * risk_criteria.txt
    * data_classification.txt

[ ] CONFIGURE AGENT
    File: asset-manager/config/agents/your-use-case.yaml

    Steps:
    1. Copy laptop-refresh.yaml as template
    2. Update agent_config.name
    3. Write system instructions:
       * Process steps
       * Required information
       * Policy compliance rules
       * Tone and style
    4. Specify tools (tool groups from MCP)
    5. Specify knowledge base
    6. Test and iterate

    Example for PIA:
    name: pia-specialist
    instructions: |
      You are a privacy specialist helping employees complete Privacy
      Impact Assessments. Guide them through these steps:
      1. Collect project information
      2. Ask privacy-specific questions
      3. Assess risk level
      4. Generate PIA document
      5. Submit to compliance team
    tool_groups:
      - compliance-tools
      - hr-tools
    knowledge_base: pia-knowledge

[ ] UPDATE ROUTING AGENT
    File: asset-manager/config/agents/routing-agent.yaml

    Steps:
    1. Add your use case to routing instructions
    2. Define keywords/triggers for routing
    3. Test routing logic

    Example:
    "If user mentions privacy, data protection, PIA, or assessment,
    route to pia-specialist agent."

[ ] CREATE EVALUATIONS
    Directory: evaluations/conversations_config/conversations/your-use-case/

    Steps:
    1. Define success flow conversation
    2. Define edge case conversations:
       * Missing information
       * Policy violations
       * System errors
    3. Create custom metrics in get_deepeval_metrics.py
    4. Run evaluation pipeline
    5. Iterate based on results

    Example metrics for PIA:
    * All required questions asked
    * Risk assessment accurate
    * PIA document complete
    * Compliance submission successful

[ ] CONFIGURE COMMUNICATION CHANNELS

    Steps:
    1. Decide which channels (Slack, email, API)
    2. Set up integration credentials
    3. Configure in Helm values
    4. Test delivery

    Example for PIA:
    * Slack for user interaction
    * Email to notify compliance team
    * API for integration with project management

[ ] UPDATE HELM VALUES
    File: helm/values.yaml

    Steps:
    1. Add environment variables for new MCP servers
    2. Add secrets for API credentials
    3. Configure integration settings
    4. Deploy and test

[ ] BUILD AND DEPLOY

    Steps:
    1. Build MCP server images: make build-mcp-your-use-case-image
    2. Push images: make push-mcp-your-use-case-image
    3. Deploy: make helm-upgrade NAMESPACE=$NAMESPACE
    4. Verify asset registration
    5. Test end-to-end flow

[ ] RUN EVALUATIONS

    Steps:
    1. Execute predefined conversations
    2. Generate synthetic conversations
    3. Evaluate with custom metrics
    4. Iterate on agent configuration
    5. Repeat until metrics meet targets

────────────────────────────────────────────────────────────────────────────

7.3 Development Best Practices

AGENT CONFIGURATION:
* Keep system instructions clear and concise
* Use numbered steps for processes
* Include examples in prompts
* Test with diverse user inputs
* Iterate based on evaluation results

KNOWLEDGE BASE:
* One topic per document
* Keep documents under 2000 words
* Use clear headings and structure
* Update regularly
* Version control in git

MCP SERVERS:
* One MCP per external system
* Clear tool names and descriptions
* Comprehensive error handling
* Unit tests for all tools
* Document authentication requirements

EVALUATIONS:
* Start with happy path
* Add edge cases gradually
* Create metrics aligned with business goals
* Run evaluations in CI/CD
* Track metrics over time

DEPLOYMENT:
* Start with testing mode
* Validate with staging environment
* Monitor metrics in production
* Have rollback plan
